# Design: Webhooks for the audit trail

**Status:** agreed · **Date:** 2026-11-24 · **Issue:** clavia-auth/clavia#18 ·
**Specifications:** the Standard Webhooks specification (headers, signature, secrets, retries), RFC 2104 (HMAC),
RFC 9110 §15 (status codes), the audit trail as `GET /api/v1/audit-events` describes it

## 1. Summary

The audit trail records every sign-in, token, change and refusal, and the only way to learn of one
is to poll `GET /api/v1/audit-events`. A deployment that feeds a SIEM, provisions accounts in
another system, or alerts on a replayed refresh token has to poll, page and remember where it was.

This design lets an operator register **webhook endpoints**: https URLs that receive each audit
event they subscribe to, as it is recorded, signed so the receiver knows it came from this server.

- **What is sent is the audit event**, exactly as the Management API renders it: one
  representation, already reviewed for what it may hold (facts, never secrets).
- **Deliveries follow Standard Webhooks**: its headers, its HMAC-SHA256 signature, its secret format,
  so a receiver can verify with any of its libraries.
- **Delivery is reliable**: an outbox written with the event, a worker that sends and retries over
  a day, at least once.
- **Every send goes through `OutboundUrlPolicy`**, at registration and again at each attempt.

### Goals

- Endpoints managed through the Management API (and then the dashboard): URL, the event types
  wanted, enabled or not, a server-generated secret shown once and rotated with an overlap.
- Signed, retried deliveries; a log of recent attempts per endpoint; a test event on demand.
- Nothing leaves the server that the audit trail does not already hold.

### Not in scope

- **Events beyond the audit trail** (a changed profile's new values, a token itself): the trail is
  the contract, and widening it is a change to the trail, not to webhooks.
- **Ordering**: deliveries are independent and may arrive out of order; each carries its time.
- **Other transports** (a queue, a stream, SNS/EventBridge): an adapter behind the same outbox later.
- **Mutual TLS or OAuth to the receiver**: the signature authenticates the sender; the receiver's
  TLS certificate authenticates the receiver.
- **Webhooks that change behaviour** (blocking a sign-in on a hook's answer): that is code at
  issuance, out of scope as in the custom claims design.

## 2. Decisions

| Topic | Decision | Why (alternatives rejected) |
|---|---|---|
| What is sent | The **audit event as `GET /api/v1/audit-events` renders it** (`id`, `type`, `occurred_at`, `outcome`, `actor`, `target`, `details`, `client_address`, `user_agent`), wrapped as Standard Webhooks' `{type, timestamp, data}` | One representation, one review. The trail refuses secret-like detail names (`LogicException`) and records a change's fields, never values, so what it holds is safe to send. A payload of its own would be a second contract to keep honest |
| Who may register | **`create:webhooks` and `read:audit_events`** together | An endpoint streams the trail. Without the second scope, a caller who may not read the trail could read it anyway by pointing a webhook at itself |
| Signature | Standard Webhooks: `webhook-id`, `webhook-timestamp`, `webhook-signature: v1,<base64 HMAC-SHA256 of "id.timestamp.body">` | A published scheme with libraries in every language, and the timestamp in the signed content lets a receiver refuse a replay. A scheme of Clavia's own would make every receiver write its own verifier |
| The secret | **Generated by the server** (`whsec_` and 32 random bytes, base64), **shown once** at creation and at rotation, kept sealed with `SecretCipher` (`webhook:<id>:secret`), never hashed | It must be read back to sign, so it is sealed like a TOTP seed, not hashed like a client secret. An operator-chosen secret would be a guessable one |
| Rotation | `POST …/rotate-secret` returns a new secret; the old one **keeps signing beside it for 24 hours** (two signatures in the header, which the format allows), then is dropped | A receiver updates its secret without losing a delivery in between |
| Reliability | An **outbox**: a delivery row per matching endpoint, written in the transaction that appends the audit event; a worker sends | A delivery from a rolled-back change cannot exist, and one from a committed change cannot be lost. Sending after the response (`DeferredTasks`) would lose every event of a crashed worker and every one that fails once |
| The worker | **`bin/clavia webhooks:deliver`**, every minute, claiming due deliveries with `FOR UPDATE SKIP LOCKED`, at most one in flight per endpoint, for at most 50 seconds a run | Like `jobs:run`: share-nothing PHP-FPM keeps no long-lived process. Latency is up to a minute, which a trail stream tolerates (§10, question 1) |
| Retries | After the first attempt: 5 s, 5 min, 30 min, 2 h, 5 h, 10 h, 10 h (Standard Webhooks' schedule), each with ±10 % jitter; then **abandoned** | About a day and a half of an endpoint being down is survivable without the operator. Endless retries would make a dead endpoint a growing queue |
| Success | A **2xx** within the timeout; anything else (a 3xx too: no redirect is followed) is a failure | Following a redirect would send the event to a URL nobody registered, past the checks of `OutboundUrlPolicy` |
| A dead endpoint | **Disabled** when every attempt has failed for 5 days running; `webhook.disabled` in the trail; enabled again by an operator | It stops filling the outbox for nobody, and says so where operators look |
| Filtering | Each endpoint lists the **event types** it wants (`*` for all), checked against `AuditEventType` | `token.issued` is most of the trail: an endpoint for configuration changes should not receive it. Subscribing to a type that does not exist is a `422`, so a typo is not a silent never |
| Volume | At most **20 endpoints**; deliveries kept **7 days** after they end, then purged by the worker; the payload is built at send time from the audit row | The audit row is immutable (a trigger refuses `UPDATE`), so the outbox stores its id only. A purged audit event (`audit:purge`) takes its pending deliveries with it (a cascade) |
| Timeouts | 5 s to connect, 10 s in all (`HttpClientFactory`'s), no body read beyond 1 KiB | A slow receiver must not hold the worker; nothing in a receiver's answer matters but its status |
| What is kept of an answer | The **status code**, the duration, and a failure category (`timeout`, `refused_url`, `connection`, `status`), never the body or headers | A receiver's answer is not this server's to store, and could carry anything |
| URLs | https only, through **`OutboundUrlPolicy`** at registration and at every attempt, connecting to the addresses checked (`PinCheckedAddresses`); `CLAVIA_OUTBOUND_ALLOW_PRIVATE_ADDRESSES` waives it in development | The rule every operator-supplied URL already follows (back-channel logout, OIDC discovery). Checking at send time too catches a name that now resolves somewhere private |
| Test event | `POST …/test` queues a `webhook.test` delivery to that endpoint only, through the same outbox | An operator checks their receiver without waiting for a real event; the same path means the same signature and checks |

## 3. Settings

None. The bounds above are constants (`WebhookEndpoint::MAX_ENDPOINTS`, the retry schedule, the
retention), like the bulk jobs' limits; a setting comes when someone needs another value.
`CLAVIA_OUTBOUND_ALLOW_PRIVATE_ADDRESSES` applies as it does everywhere.

## 4. Model

### Domain

A new context, `Domain\Webhook`:

- `WebhookEndpoint` (aggregate): id (`wh_…`), `Url`, description, `EventFilter` (a set of
  `AuditEventType`, or all), enabled or disabled (with the reason and when), the sealed current
  secret, an optional previous one with the instant it stops signing, created and updated.
  `rotateSecret()`, `disable()`, `enable()`, `withFilter()`, `matches(AuditEventType)`.
- `WebhookSecret` (value object): `generate(RandomSource)`, `whsec_` and 32 bytes; never printed by
  `__toString`, `#[\SensitiveParameter]` wherever it travels.
- `WebhookDelivery`: endpoint, audit event id (or the test marker), status (`pending`, `succeeded`,
  `failed`, `abandoned`), attempt count, next attempt at, the last attempt's status code, duration
  and failure category.
- `RetrySchedule`: the delays of §2 and the jitter, from a `RandomSource`.
- Repositories: `WebhookEndpointRepository`, `WebhookDeliveryRepository` (`enqueueFor(AuditEvent)`,
  `claimDue(now, limit)`, `record()`, `purgeEndedBefore()`).
- Events: `WebhookCreated`, `WebhookChanged`, `WebhookDeleted`, `WebhookSecretRotated`,
  `WebhookDisabled`, recorded by the configuration trail (`webhook.*`).

### Application

- `Webhooks\Manage*`: create (returns the secret once), change, delete, rotate, enable, test.
- **Fan-out**: `Audit` (the application's recorder) asks `WebhookDeliveryRepository::enqueueFor()`
  right after `AuditLog::append()`, in the same transaction. One `INSERT … SELECT` over the enabled
  endpoints whose filter matches; nothing when there are none.
- `DeliverWebhooks` (`webhooks:deliver`): claim, check the URL, build the body from the audit row,
  sign, send through the `WebhookSender` port, record, schedule the next attempt or end; disable the
  endpoints dead for five days; purge.
- Port `WebhookSender` (`send(Url, headers, body): SendOutcome`), adapter on PSR-18 with
  `PinCheckedAddresses`; a double that records.

### Migrations

`webhook_endpoints` (the secret columns sealed) and
`webhook_deliveries` (`audit_event_id` references `audit_events` `ON DELETE CASCADE`, a partial index
on due pending deliveries, `endpoint_id` `ON DELETE CASCADE`).

## 5. Flows

### 5.1 Registering

`POST /api/v1/webhooks` with `url`, `description`, `events`: the URL through `OutboundUrlPolicy`
(`422` with the reason category, never the resolved address), the event types known (`422` per
unknown one), at most twenty endpoints (`409`). The answer, `201`, carries the secret once. The
trail records `webhook.created` with the URL's host and the event types.

### 5.2 An event recorded

1. A use case's subscriber records an audit event through `Audit`, inside the use case's
   transaction (or outside, for a refusal, as today).
2. `Audit` appends it, then `enqueueFor()` inserts one pending delivery per enabled endpoint whose
   filter matches, due now.
3. A rollback removes both; a commit keeps both.

### 5.3 Delivering

1. The worker claims up to 100 due deliveries, at most one per endpoint, `FOR UPDATE SKIP LOCKED`,
   and marks them in flight for 30 s (so a crashed worker's claim comes back).
2. For each: the endpoint is still enabled (or the delivery is abandoned); the URL passes
   `OutboundUrlPolicy` again (`refused_url` otherwise, a failure); the body is built from the audit
   row; it is signed with the current secret, and with the previous one while it lasts.
3. Sent with the timeouts of §2. A 2xx is `succeeded`. Anything else records the status or the
   category, and schedules the next attempt from `RetrySchedule`, or `abandoned` after the last.
4. Endpoints whose deliveries have all failed for five days are disabled (`WebhookDisabled`).
5. Deliveries ended more than seven days ago are purged. The run stops after 50 seconds, leaving
   the rest for the next minute.

### 5.4 Rotating, testing, reading the log

- `POST /api/v1/webhooks/{id}/rotate-secret`: a new secret, returned once; the old one signs beside
  it for 24 hours.
- `POST /api/v1/webhooks/{id}/test`: a `webhook.test` delivery queued (`202`), sent by the worker.
- `GET /api/v1/webhooks/{id}/deliveries`: the last deliveries, newest first, with their status,
  attempts and last answer's code and category, never a body.

## 6. Interfaces

- **Management API**:
  - `GET|POST /api/v1/webhooks`, `GET|PATCH|DELETE /api/v1/webhooks/{id}` (`url`, `description`,
    `events`, `is_enabled`);
  - `POST …/rotate-secret`, `POST …/test`, `GET …/deliveries`;
  - scopes `read:webhooks`, `create:webhooks`, `update:webhooks`, `delete:webhooks`; creating,
    changing the URL or the events, and testing also need `read:audit_events`;
  - the payload documented as a schema (`WebhookPayload`, whose `data` is the `AuditEvent`), with a
    signed example and how to verify it.
- **Console**: `bin/clavia webhooks:deliver`, every minute (README, CLAUDE.md).
- **Dashboard** (clavia-dashboard): a Webhooks page (list, create with the secret shown once,
  edit, enable, rotate, test, the delivery log).

## 7. Security rules

- **Nothing is sent that the trail does not hold**, and the trail holds no secret: its detail names
  are refused, and a change lists fields, never values. A webhook adds no field of its own but the
  envelope.
- **No SSRF**: https only, `OutboundUrlPolicy` at registration and at each attempt, the checked
  addresses pinned, no redirect followed, bodies not read.
- **Streaming the trail needs the right to read it**: `read:audit_events` beside the webhook scope.
- **The secret is the server's**: generated, shown once, sealed with a row-specific context, never
  logged, never in the trail, never in a delivery log.
- **A receiver can verify and refuse replays**: the signature covers the id and the timestamp, and
  the document tells receivers to refuse a timestamp more than five minutes off.
- **A receiver cannot make this server store or echo anything**: only the status, a duration and a
  category are kept.
- **A slow or dead receiver cannot hold the server**: one delivery in flight per endpoint, timeouts,
  a bounded run, a bounded schedule, and disablement.

## 8. Tests

- Domain: `WebhookSecretTest` (format, never printed), `RetrySchedule` (delays, jitter bounds,
  the end), `WebhookEndpoint` (filters, rotation overlap, disablement).
- A contract for each repository, against the doubles and PostgreSQL: the outbox written and rolled
  back with its transaction, claims shared by no two workers, one in flight per endpoint, purge and
  cascade.
- `WebhookSender`: the signature as a known answer computed with a Standard Webhooks reference
  library, two signatures
  during an overlap, no redirect followed, the body not read.
- Acceptance:
  - an endpoint registered (with both scopes, and refused without `read:audit_events`), an audit
    event delivered and verified with the secret;
  - a failure retried on the schedule (frozen clock), then abandoned; a dead endpoint disabled;
  - a private address refused at registration and at send time;
  - the test event; the delivery log with no body;
  - every response checked against the OpenAPI document; the `webhook.*` events in their trail.

## 9. Slices

1. **Endpoints.** `Domain\Webhook` (endpoint, secret, filter), the migration for endpoints, the
   Management API (CRUD, rotate), the scopes, the configuration trail. *Done when* an operator can
   register, change, rotate and delete an endpoint, the secret is shown once and stored sealed, and
   every refusal of §5.1 is covered; nothing is delivered yet.
2. **Delivery.** The outbox written by `Audit`, `webhooks:deliver`, signing, `WebhookSender`, the
   retry schedule, the purge. *Done when* an audit event reaches an endpoint signed and verifiable,
   a failure is retried and then abandoned, and a rolled-back change sends nothing.
3. **Operating them.** The delivery log, the test event, disablement of dead endpoints, the payload
   schema and verification guide in the document. *Done when* an operator can see why deliveries
   fail and test a receiver, and a dead endpoint stops itself.
4. **Dashboard** (clavia-dashboard): the Webhooks page. *Done when* all of the above is possible
   without the API.

## 10. As built

What the slices settled differently from the sections above, so the code and this document agree.

- **Endpoint ids are UUIDs**, as initial access tokens' are, not `wh_…`.
- **The worker claims endpoints, not deliveries** (§2, "The worker"; §5.3): `webhook_endpoints`
  carries `delivering_until`, set with `FOR UPDATE SKIP LOCKED`. Claiming deliveries could not keep
  one in flight per endpoint: two workers would each lock a different delivery of the same
  endpoint. A worker sends an endpoint's due deliveries one at a time, and a failure stops that
  endpoint for the run.
- **A timeout is a `connection` failure**: PSR-18 does not tell a timeout from a refusal without a
  vendor's exception, and the category tells an operator the same thing either way.
- **The answer is never downloaded** rather than read up to 1 KiB: the sender's client is built with
  `stream`, and the body is closed unread.

## 11. Open questions

1. **A minute of latency** (§2, the worker)? *Recommendation:* accept it for now. A trail stream is
   read by machines that tolerate it. If not, the worker can also run after a response
   (`DeferredTasks`) for the deliveries just written, through the same claim, without changing the
   outbox.
2. **Client address and user agent in the payload**? They are personal data, and the audit API
   already returns them to `read:audit_events`. *Recommendation:* send them, as the API does, since
   registering requires that scope. A per-endpoint switch to leave them out can come later.
3. **`token.issued` by default**? *Recommendation:* no default: an endpoint names its types or `*`,
   and the dashboard suggests the configuration and security events first, since `token.issued` is
   most of the volume.
