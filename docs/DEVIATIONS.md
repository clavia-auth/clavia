# Differences from the Python reference

This file records where the PHP server behaves differently from the Python reference, and
why. Parity with the Python server is not a goal — the PHP implementation follows the RFCs
and what is correct and idiomatic in PHP (see "Engineering direction" in `CLAUDE.md`). The
list exists so that someone moving a deployment or a client from one server to the other
knows what changes.

## Settings

| Setting | Python | PHP | Why |
|---|---|---|---|
| `CLAVIA_TRUSTED_PROXIES` | — (`FORWARDED_ALLOW_IPS`, read by uvicorn) | New. Addresses, CIDR ranges or `*`; empty by default | The proxy trust list was a uvicorn flag, not a Clavia setting. Under PHP-FPM the application decides, so it is a setting like any other — and the default trusts nobody. |
| `CLAVIA_DATABASE_URL` | `postgresql+psycopg://…` (SQLAlchemy) | `postgresql://…` | The `+psycopg` suffix names a Python driver. |
| `CLAVIA_SIGNING_BACKEND` custom value | `module:Class` | A fully-qualified PHP class name | Same idea, the language's own notation. |
| Empty value (`CLAVIA_X=`) | An empty string for text settings, an error for numbers | Unset, for every setting: the default applies | One rule instead of two; `.env.example` ships several empty keys. |
| Lists (`CLAVIA_SCOPES_SUPPORTED`) | JSON array only | JSON array, or comma/space separated | Easier to write in a `.env`. |

## Behaviour

| Area | Python | PHP | Why |
|---|---|---|---|
| Production warning for the `postgres` signing backend | Emitted when the process starts | Printed by every `clavia` command; not repeated per HTTP request | PHP-FPM has no "process start" for the application: it is rebuilt for each request. |
| `clavia config` values | Python literals (`True`, `['openid', …]`) | `true`, JSON arrays; an unset secret prints `<unset>` rather than `***` | Command-line output is not part of the HTTP contract. |
| `/docs`, `/openapi.json` (development only) | Generated by FastAPI | Not served | They were a FastAPI convenience. The Management API's OpenAPI document arrives with Step 6, as a file. |
| `/auth/static/*`, `/favicon.ico` | Served by the application | Served by Caddy from `public/` | Static files do not need PHP. Same URLs, same media types, same caching. |
| Secrets longer than 72 bytes (passwords, client secrets) | Passed to bcrypt as they are (truncated or rejected depending on the bcrypt version installed) | Refused when hashing, never a match when verifying | bcrypt reads 72 bytes at most. A hash that silently covers less than what was typed makes every longer password sharing that prefix equivalent. |
| Console command names | Typer groups, separated by a space: `clavia secrets generate-key`, `clavia keys rotate` | Namespaced with a colon: `clavia secrets:generate-key`, `clavia keys:rotate` | `symfony/console`'s notation. Not part of the HTTP contract. |
| Schema migrations | Alembic revisions generated from the models (`alembic upgrade head`) | Plain SQL files in `migrations/`, applied by `clavia db:migrate`, listed by `clavia db:status`; forward-only | No ORM to generate from. The files are the schema's source of truth. |

## OAuth2 endpoints

| Area | Python | PHP | Why |
|---|---|---|---|
| Invalid authorization request, once the client and redirect URI are known (missing or `plain` PKCE, unknown scope, bad `response_type`…) | `400` with a JSON error document | `302` to the registered redirect URI with `error`, `error_description`, `state` and `iss` | RFC 6749 §4.1.2.1: once the redirect URI is established, the error belongs to the client. A JSON page in the user's browser tells the application nothing and strands the user. |
| Order of validation at `/oauth2/authorize` | `response_type` first (Authlib), so an `unsupported_response_type` error could be redirected to a URI not yet checked | Client, then redirect URI, then everything else | Nothing may ever be sent to a redirect URI that was not matched against the registration. |
| A request parameter sent more than once | One of the values was used, silently | Refused: `invalid_request` (not redirected when it is `client_id` or `redirect_uri`) | RFC 6749 §3.1 forbids repetition; two components picking different values is how parameter-pollution attacks work. |
| `code_challenge` format | Any string | Exactly 43 characters of the base64url alphabet | That is what the S256 of anything looks like (RFC 7636 §4.2). A value that cannot be a SHA-256 is refused when the code is requested, not discovered when it is redeemed. |
| Missing `grant_type` at `/oauth2/token` | `unsupported_grant_type` | `invalid_request` | RFC 6749 §5.2: a missing required parameter is `invalid_request`. An unknown value is still `unsupported_grant_type`. |
| Token exchange | Code marked used and token written in separate steps | One transaction on the locked code row | Two concurrent redemptions of one code cannot both succeed, and the loser is treated as a replay: the winner's token is revoked (RFC 6749 §4.1.2). |
| Client authentication at `/oauth2/token` | Each method tried in turn (Authlib): failed Basic credentials fell through to a `client_id` in the body | One method per request, read from what it carries. A failed or non-Basic `Authorization` header fails the request; so does Basic together with a body `client_secret` or another client's `client_id` | RFC 6749 §2.3: a client must not use more than one authentication method in a request. |
| Client identifiers | Any string | 1–64 visible ASCII characters, no colon | A colon cannot be carried in HTTP Basic credentials (RFC 7617 §2). Generated identifiers were never affected. |
| List columns of `oauth2_clients` (`redirect_uris`, `grant_types`, `response_types`) | `JSON` | `jsonb`, each constrained to be an array | Not visible over HTTP. `jsonb` can be indexed and compared. |
| Columns not used yet (`sid`, `is_first_party`, `is_system`, `enforce_policies`, per-connection email uniqueness…) | Present from the first revision that needed them | Added by the step that introduces the behaviour (`nonce`, `auth_time`, `amr` and the profile fields arrived with Step 4; `audience` on access tokens, the APIs and the client grants with Step 5) | Migrations are written as the port advances; `users.email` is unique on its own until connections arrive (Step 13). |

## Client Credentials

| Area | Python | PHP | Why |
|---|---|---|---|
| A client registered as public that holds a secret | Could be stored; the grant refused it with `unauthorized_client` | Cannot be stored: the registration and the table both refuse it | Inconsistent registration data fails closed at the earliest point. With no such client possible, the grant has no confidential-client check of its own: `none` is not among its accepted methods, so a public client never gets past client authentication. |
| `clavia clients:create-m2m` | Printed the secret again inside the example `curl` command; `--secret` took any string; `--third-party` | The secret is printed once, the example uses a placeholder; a chosen secret has at least 32 characters (a generated one, 43); no `--third-party` until application ownership exists (Step 12) | A secret repeated in a copy-pasteable command ends up in shell histories. |
| Registering an API and granting a client on it from the shell | `clavia management-api register`, `clavia clients grant` | `clavia management-api:register`, `clavia clients:grant` (and `management-api:scopes`), arrived with the Management API in Step 6 | symfony/console names commands `group:name`; every other command already follows it. |

## Management API

| Area | Python | PHP | Why |
|---|---|---|---|
| The contract | Generated by FastAPI from the Pydantic models | Written first, as `docs/openapi/management-api.yaml`; every request is validated against it before a handler runs, and the acceptance tests check every response against it. The scope an operation needs is read from its `security` requirement | One statement of the API, enforced in both directions: a route cannot quietly demand another scope, and a response cannot drift from the document. |
| Error bodies | `{"detail": …}` (a string, or FastAPI's list of validation errors) | RFC 9457 problem documents (`application/problem+json`: `type`, `title`, `status`, `detail`, and for a request the contract refused, `errors` with an RFC 6901 `pointer` or a `parameter`). Bearer failures stay RFC 6750 documents | A documented, standard shape instead of a framework's. The value at fault is never repeated in an error — it may be a password. |
| Statuses for an unreadable request | 422 for everything Pydantic refused | 400 for malformed JSON or a query parameter sent twice, 415 for a body that is not `application/json`, 422 for a request the contract or the domain refuses | Each tells the caller what to fix. Parameters are never silently "last one wins". |
| Order of the checks | Authentication, then FastAPI's validation and the scope dependency in declaration order | Credentials, token and audience (401), scope (403), then the request (400/415/422) | A caller without the scope learns nothing about what the operation would have accepted. |
| `token_endpoint_auth_method` when omitted | One default for every client | `none` for a public client, `client_secret_basic` for a confidential one | The only coherent value for each type; RFC 6749 §2.3.1 requires every server to support Basic. |
| The code flow on a registration | `authorization_code` and the `code` response type checked separately | They must come together, and either needs a redirect URI | Half of the code flow is a client no request can succeed for, refused where the mistake is made (also by `PATCH`). |
| Grant types and fields not built yet | The device grant, `allowed_connections`… | Absent from the contract, so refused as unknown; they arrive with their steps | A field the server would ignore is a promise it does not keep. |
| Management scopes | Included roles and connections | Users, clients, APIs and roles; the connection scopes arrive with Step 13 | A scope no route checks would be granted for nothing. |
| `audience` in a user's flow | Checked at the authorization endpoint | Checked there, stored on the code, and checked again at redemption: a permission withdrawn meanwhile is not issued, and a code for an API deleted meanwhile is `invalid_grant` | Scope is narrowed at issuance and re-checked at redemption, not trusted from authorization time. |
| `seed-dev` | Created the machine client and granted it the Management API | The same, with a fixed, printed secret (`dev-m2m-secret-for-local-development-only`) and the token request to run | A development deployment should reach `/api/v1/*` straight after seeding. |
| Missing credentials | `401` with a bare challenge and `{}` | The same, at `/oidc/userinfo` too; the realm is the Management API's identifier here and the issuer there | RFC 6750 §3.1: no error information when nothing was presented; every refusal is still a JSON document. |

## OpenID Connect

| Area | Python | PHP | Why |
|---|---|---|---|
| ID token `aud` | A one-element array: `["client-id"]` | The client id as a string | OIDC Core §2 allows either for a single audience; a string is what every relying party library accepts, and no `azp` is then needed. |
| Discovery document | Advertised every grant, `prompt_values_supported`, `frontchannel_logout_supported` and the endpoints of the finished server | Names only what this build does: `grant_types_supported` lists the grants the token endpoint answers (`authorization_code`, `client_credentials`); `prompt_values_supported`, the introspection, revocation, device and end-session endpoints and `sid` appear with the steps that implement them | The document is a contract a relying party configures itself from. Fields whose specification default differs from the server (`request_uri_parameter_supported`, `response_modes_supported`, `grant_types_supported`) are always stated. |
| `nonce` outside an OpenID Connect request | Recorded and replay-checked whatever the scope | Ignored when `openid` was not requested | Only an authentication request has a nonce (OIDC Core §3.1.2.1); elsewhere it is an unknown parameter, which RFC 6749 §3.1 says to ignore. |
| `nonce` format | Any string | 1–512 bytes of UTF-8, no control characters; anything else is `invalid_request` | The value is stored and copied into a signed token. No legitimate relying party sends more. |
| How long a used nonce is remembered | Four times the authorization code lifetime | The code lifetime plus the ID token lifetime | A bound with a reason: until neither the code carrying the nonce nor an ID token minted from it can still be valid. |
| An ID token that cannot be signed (no active key) | The request failed with a server error | The whole exchange is rolled back: no access token is issued, and the code stays unspent for a retry once a key exists | A client must never receive an access token without the ID token it asked for. |
| `clavia keys:generate` when a key is already active | Created a new active key and withdrew the old one from the JWKS at once | Refused, pointing to `clavia keys:rotate` | Withdrawing a key immediately breaks every live token it signed; replacing a key is what rotation (with its grace period) is for. |
| Signing backends other than `postgres` | Implemented | Refused by name when the server first needs a signer, until Step 19 | An operator who configured a KMS must never end up signing from PostgreSQL without knowing it. |
| Userinfo credentials | The `Authorization` header; an `access_token` also sent in the query or the body was ignored | The `Authorization` header only; a token also sent in the query or the body is `invalid_request` | RFC 6750 §2: one method per request. Tokens in URLs and bodies end up in logs; OAuth 2.1 drops the query form. |
| Userinfo without usable credentials | `401` with `error="invalid_request"`, whether the header was missing or malformed; no `realm` | No credentials: `401` with `WWW-Authenticate: Bearer realm="…"`, no error code and an empty JSON object as the body. A malformed `Bearer` header: `400 invalid_request`. Every challenge names the issuer as its realm | RFC 6750 §3.1: a request with no authentication information gets no error code, and `invalid_request` is a 400. |
| Profile claims | Any string in the column | Names of at most 255 characters without control characters, `picture` an http(s) URL, `locale` a BCP 47 tag | They are copied into signed tokens; the domain refuses what no relying party should receive. |

## Login page and sessions

| Area | Python | PHP | Why |
|---|---|---|---|
| A throttled sign-in attempt | Refused at once, without hashing anything | Refused after the same time a password check takes | A faster answer would tell an observer the account is locked — and so that it exists. |
| Theme toggle on a login page re-shown after a failed attempt | Came back to `/auth/login`, losing the pending authorization request | Comes back to `/auth/login?state=…` | Switching colour scheme must not cost the person their place in the flow. |
| `next` on `POST /auth/logout` | Any `https` URL on a registered origin | The same, without a fragment | Nothing legitimate needs one there, and a fragment is never checked by anyone. |
| Session record in Redis | A hash, plus a per-user index and a per-session client index | One JSON document per session; the two indexes come with session management and back-channel logout (Step 17) | Not visible over HTTP. Nothing reads the indexes yet. |
| The session's connection | Recorded | Not yet recorded | Connections arrive in Step 13, with the check that uses the value. |

## Multi-factor authentication

| Area | Python | PHP | Why |
|---|---|---|---|
| Wrong codes at the second step | Counted per challenge only: a challenge is destroyed after `CLAVIA_MFA_MAX_ATTEMPTS`, and the next correct password opens a fresh one | Also counted against the account and the address, by the same throttle as wrong passwords (`CLAVIA_LOGIN_MAX_ATTEMPTS` per `CLAVIA_LOGIN_ATTEMPT_WINDOW`); a throttled attempt is refused without the code being checked | Per challenge alone, anyone holding the password can guess six digits forever, five at a time. |
| Counting the wrong codes | Read, increment, write back | One Redis script (`EXISTS`, `HINCRBY`, `DEL` at the limit) | Concurrent guesses are each counted, and a challenge that expired meanwhile is not written back. |
| The challenge's connection | Recorded | Not yet recorded | As for sessions: connections arrive in Step 13. |

## Social login

| Area | Python | PHP | Why |
|---|---|---|---|
| PKCE towards GitHub | Not sent | Sent to every provider | A provider that does not implement RFC 7636 ignores the parameters; one that does gets the protection. |
| The `state` cookie | `clavia_social_state` | `clavia_external_state` | Named for what it is, whatever kind of provider. |
| Where a matching address is looked for | The pools the application enables, and the provider's own accounts | Every account, until connections exist (Step 13) | There are no pools yet. |

## Refresh tokens

| Area | Python | PHP | Why |
|---|---|---|---|
| The ceiling of a refresh | The scope the previous access token carried — narrowed by roles | What was authorized, or what the client narrowed it to since; roles narrow each access token, not the chain | A role taken away and given back is honoured by the next refresh instead of needing a new sign-in. |
| Roles taken away, at a refresh | `access_denied`, the token spent | `invalid_grant`, the token not spent | `access_denied` is not a token-endpoint error (RFC 6749 §5.2); only a refresh that succeeds spends the token. |
| A deactivated account, at a refresh | Refused after the token was spent | Refused before | The same rule: `used` means refreshed. |
| Revoking a family's access tokens | Through a `refresh_token_id` on each access token | A `refresh_family_id` on each access token | One statement revokes them, whatever became of the tokens in between. |
| Concurrent refreshes of one token | A threaded acceptance test | Not raced in a test: PHP-FPM has no threads in a test. The row lock is the guarantee, and the contracts prove the lock is taken inside a transaction | The behaviour is the database's, not the code's. |

## Consent

| Area | Python | PHP | Why |
|---|---|---|---|
| Where ownership is stored | An `is_first_party` column, and the `tpc_` prefix on the id | The prefix alone: a third-party id starts with `tpc_`, a generated first-party id is letters and digits | One fact in one place. Ownership is identity, fixed at registration, and the id is where it is visible without a lookup; a column could only disagree with it. |
| A consent's API | Its identifier as text, with `''` standing for "no API" | A foreign key onto `resource_servers`, null for no API, kept to one row by `UNIQUE NULLS NOT DISTINCT` | Deleting an API takes the consents given for it along, as every other link does. |
| `allow_skipping_consent` on a system API | May be turned off | Always on (409 to turn it off) | Only first-party applications reach a system API, and they are the operator's own: there is nobody to ask. |
| `prompt` | Every value of OIDC Core §3.1.2.1 | `none` and `consent`; `login` and `select_account` are ignored until Step 18, and `prompt_values_supported` is not advertised yet | The two values consent needs; the rest belong to the step that makes re-authentication part of the authorize decision. `prompt=none` with nobody signed in is `login_required` already. |
| Resuming a request after sign-in or consent | The request's own URL | A `GET` to the endpoint carrying every parameter in its query | A request posted to `/oauth2/authorize` was resumed without its parameters; now it is resumed whole. |
| Refusing at the consent screen | `303` to the application | `302`, with `iss` (RFC 9207) like every authorization response | One way an authorization response travels. |
| Withdrawing a consent | `DELETE …/consents/{client_id}`, `update:users` | The same | — |

## Roles

| Area | Python | PHP | Why |
|---|---|---|---|
| Redeeming a code after the person's roles were taken away | `access_denied` from the token endpoint | `invalid_grant` | `access_denied` is not a token-endpoint error (RFC 6749 §5.2); the grant is what became worthless. The authorization endpoint still answers `access_denied` before a code exists. |
| Taking a role from people | `DELETE /api/v1/roles/{id}/users` with `{"user_ids": […]}` | `DELETE /api/v1/roles/{id}/users/{user_id}`, one account per request; the dashboard sends one each | OpenAPI 3.0 gives a `DELETE` body no meaning, and intermediaries may drop it. |
| Giving a role | `200` with every holder | `204` | The holders are a page of their own (`GET …/users`); a list that grows has no place in a response that does not page it. |
| The holders of a role | By email, searchable | Most recently given first, not searched | The assignments are one table and know no address; the list is short, and finding a person is `GET /api/v1/users?q=`. |
| Roles listed | Alphabetically | Newest first, like every other list (`roles:list` is alphabetical) | One ordering across the API. |
| An unknown role or account in an assignment | `404`, some assignments possibly written | `404`, nothing written | A request is applied whole or not at all. |
| Role names and descriptions | Any string up to 64 / 500 characters | One line, and a name not blank | They are labels shown in lists and pickers. |
| Saving an API | Permission rows updated in place | The same, now required: rows are reconciled, never replaced | A role holds a permission by a foreign key onto its row; replacing the rows would take every role's grant of them along. |
| `roles create` / `roles assign` / `roles list` | Typer subcommands | `roles:create` (`--audience`, `--scope`, `--description`), `roles:assign`, `roles:list` | The CLI's `group:verb` convention. |

## RP-Initiated Logout

| Area | Python | PHP | Why |
|---|---|---|---|
| `post_logout_redirect_uri` | Accepted when its origin is the origin of any client's redirect URI | Must be one of the `post_logout_redirect_uris` the identified client registered, matched exactly (new client field) | RP-Initiated Logout 1.0 §3.1. An origin rule lets any page on a client's site — or another client's — be the landing page. |
| Which client asks | Not considered | The hint's audience, or `client_id`; both present and different counts as neither | §2: the OP must verify that `client_id` matches the ID token's. |
| `state` | Ignored | Returned on the post-logout redirect | §3. |
| A request without a valid hint, while signed in | Redirected, the session left in place, the cookie deleted anyway | A page asking whether to sign out; the session and its cookie stay until the person confirms | §2: the OP should ask. Deleting the cookie of a session left alive only signs the person out of this browser by accident. |
| `POST /oidc/logout` | Not served | Served, as §2 requires | |

## Errors shown to browsers

| Area | Python | PHP | Why |
|---|---|---|---|
| 404 and 405 | `{"detail": …}` for every caller | The same for a program; a page for a browser (`Accept` naming `text/html`) | A person who follows a dead link should read a sentence, not a JSON document. Programs keep the body they parse. |
| `/oauth2/authorize` error that cannot be redirected (unknown client, unregistered redirect URI) | A JSON error document | The same for a program; a page for a browser, explaining what happened, with the error code as a reference and no link onwards | RFC 6749 §4.1.2.1: the resource owner is to be informed, and the resource owner is in a browser. |
| An uncaught error (500) | `Internal Server Error` in plain text | The same for a program, plus `X-Error-Reference`; a page with the reference for a browser | The reference is in the log next to the cause, so a person can report the failure without the server describing it. |

## Tooling (not user-visible)

- Console commands are built on `symfony/console` directly rather than `laminas-cli`, which wraps
  it: `bin/clavia <command>` keeps the Python command names without a second binary.
- The licence header is enforced by a test (`LicenseHeaderTest`) instead of an extra tool.
- The auth pages are laminas-view PHP templates rendered through Mezzio's
  `TemplateRendererInterface`, where Python used Jinja2. Markup and the stylesheet are the same.
