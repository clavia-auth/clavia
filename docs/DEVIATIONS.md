# Differences from the Python reference

This file records where the PHP server behaves differently from the Python reference, and
why. Parity with the Python server is not a goal — the PHP implementation follows the RFCs
and what is correct and idiomatic in PHP (see "Engineering direction" in `CLAUDE.md`). The
list exists so that someone moving a deployment or a client from one server to the other
knows what changes.

## Settings

| Setting | Python | PHP | Why |
|---|---|---|---|
| `CLAVIA_TRUSTED_PROXIES` | — (`FORWARDED_ALLOW_IPS`, read by uvicorn) | New. Addresses, CIDR ranges or `*`; empty by default | The proxy trust list was a uvicorn flag, not a Clavia setting. Under PHP-FPM the application decides, so it is a setting like any other — and the default trusts nobody. |
| `CLAVIA_DATABASE_URL` | `postgresql+psycopg://…` (SQLAlchemy) | `postgresql://…` | The `+psycopg` suffix names a Python driver. |
| `CLAVIA_SIGNING_BACKEND` custom value | `module:Class` | A fully-qualified PHP class name | Same idea, the language's own notation. |
| Empty value (`CLAVIA_X=`) | An empty string for text settings, an error for numbers | Unset, for every setting: the default applies | One rule instead of two; `.env.example` ships several empty keys. |
| Lists (`CLAVIA_SCOPES_SUPPORTED`) | JSON array only | JSON array, or comma/space separated | Easier to write in a `.env`. |

## Behaviour

| Area | Python | PHP | Why |
|---|---|---|---|
| Production warning for the `postgres` signing backend | Emitted when the process starts | Printed by every `clavia` command; not repeated per HTTP request | PHP-FPM has no "process start" for the application: it is rebuilt for each request. |
| `clavia config` values | Python literals (`True`, `['openid', …]`) | `true`, JSON arrays; an unset secret prints `<unset>` rather than `***` | Command-line output is not part of the HTTP contract. |
| `/docs`, `/openapi.json` (development only) | Generated by FastAPI | Not served | They were a FastAPI convenience. The Management API's OpenAPI document arrives with Step 6, as a file. |
| `/auth/static/*`, `/favicon.ico` | Served by the application | Served by Caddy from `public/` | Static files do not need PHP. Same URLs, same media types, same caching. |
| Secrets longer than 72 bytes (passwords, client secrets) | Passed to bcrypt as they are (truncated or rejected depending on the bcrypt version installed) | Refused when hashing, never a match when verifying | bcrypt reads 72 bytes at most. A hash that silently covers less than what was typed makes every longer password sharing that prefix equivalent. |
| Console command names | Typer groups, separated by a space: `clavia secrets generate-key`, `clavia keys rotate` | Namespaced with a colon: `clavia secrets:generate-key`, `clavia keys:rotate` | `symfony/console`'s notation. Not part of the HTTP contract. |
| Schema migrations | Alembic revisions generated from the models (`alembic upgrade head`) | Plain SQL files in `migrations/`, applied by `clavia db:migrate`, listed by `clavia db:status`; forward-only | No ORM to generate from. The files are the schema's source of truth. |

## OAuth2 endpoints

| Area | Python | PHP | Why |
|---|---|---|---|
| Invalid authorization request, once the client and redirect URI are known (missing or `plain` PKCE, unknown scope, bad `response_type`…) | `400` with a JSON error document | `302` to the registered redirect URI with `error`, `error_description`, `state` and `iss` | RFC 6749 §4.1.2.1: once the redirect URI is established, the error belongs to the client. A JSON page in the user's browser tells the application nothing and strands the user. |
| Order of validation at `/oauth2/authorize` | `response_type` first (Authlib), so an `unsupported_response_type` error could be redirected to a URI not yet checked | Client, then redirect URI, then everything else | Nothing may ever be sent to a redirect URI that was not matched against the registration. |
| A request parameter sent more than once | One of the values was used, silently | Refused: `invalid_request` (not redirected when it is `client_id` or `redirect_uri`) | RFC 6749 §3.1 forbids repetition; two components picking different values is how parameter-pollution attacks work. |
| `code_challenge` format | Any string | Exactly 43 characters of the base64url alphabet | That is what the S256 of anything looks like (RFC 7636 §4.2). A value that cannot be a SHA-256 is refused when the code is requested, not discovered when it is redeemed. |
| Missing `grant_type` at `/oauth2/token` | `unsupported_grant_type` | `invalid_request` | RFC 6749 §5.2: a missing required parameter is `invalid_request`. An unknown value is still `unsupported_grant_type`. |
| Token exchange | Code marked used and token written in separate steps | One transaction on the locked code row | Two concurrent redemptions of one code cannot both succeed, and the loser is treated as a replay: the winner's token is revoked (RFC 6749 §4.1.2). |
| Client authentication at `/oauth2/token` | Each method tried in turn (Authlib): failed Basic credentials fell through to a `client_id` in the body | One method per request, read from what it carries. A failed or non-Basic `Authorization` header fails the request; so does Basic together with a body `client_secret` or another client's `client_id` | RFC 6749 §2.3: a client must not use more than one authentication method in a request. |
| Client identifiers | Any string | 1–64 visible ASCII characters, no colon | A colon cannot be carried in HTTP Basic credentials (RFC 7617 §2). Generated identifiers were never affected. |
| List columns of `oauth2_clients` (`redirect_uris`, `grant_types`, `response_types`) | `JSON` | `jsonb`, each constrained to be an array | Not visible over HTTP. `jsonb` can be indexed and compared. |
| Columns not used yet (`sid`, `audience`, `is_first_party`, per-connection email uniqueness…) | Present from the first revision that needed them | Added by the step that introduces the behaviour (`nonce`, `auth_time`, `amr` and the profile fields arrived with Step 4) | Migrations are written as the port advances; `users.email` is unique on its own until connections arrive (Step 13). |

## OpenID Connect

| Area | Python | PHP | Why |
|---|---|---|---|
| ID token `aud` | A one-element array: `["client-id"]` | The client id as a string | OIDC Core §2 allows either for a single audience; a string is what every relying party library accepts, and no `azp` is then needed. |
| Discovery document | Advertised every grant, `prompt_values_supported`, `frontchannel_logout_supported` and the endpoints of the finished server | Names only what this build does: `grant_types_supported` is `["authorization_code"]`; `prompt_values_supported`, the introspection, revocation, device and end-session endpoints and `sid` appear with the steps that implement them | The document is a contract a relying party configures itself from. Fields whose specification default differs from the server (`request_uri_parameter_supported`, `response_modes_supported`, `grant_types_supported`) are always stated. |
| `nonce` outside an OpenID Connect request | Recorded and replay-checked whatever the scope | Ignored when `openid` was not requested | Only an authentication request has a nonce (OIDC Core §3.1.2.1); elsewhere it is an unknown parameter, which RFC 6749 §3.1 says to ignore. |
| `nonce` format | Any string | 1–512 bytes of UTF-8, no control characters; anything else is `invalid_request` | The value is stored and copied into a signed token. No legitimate relying party sends more. |
| How long a used nonce is remembered | Four times the authorization code lifetime | The code lifetime plus the ID token lifetime | A bound with a reason: until neither the code carrying the nonce nor an ID token minted from it can still be valid. |
| An ID token that cannot be signed (no active key) | The request failed with a server error | The whole exchange is rolled back: no access token is issued, and the code stays unspent for a retry once a key exists | A client must never receive an access token without the ID token it asked for. |
| `clavia keys:generate` when a key is already active | Created a new active key and withdrew the old one from the JWKS at once | Refused, pointing to `clavia keys:rotate` | Withdrawing a key immediately breaks every live token it signed; replacing a key is what rotation (with its grace period) is for. |
| Signing backends other than `postgres` | Implemented | Refused by name when the server first needs a signer, until Step 19 | An operator who configured a KMS must never end up signing from PostgreSQL without knowing it. |
| Userinfo credentials | The `Authorization` header; an `access_token` also sent in the query or the body was ignored | The `Authorization` header only; a token also sent in the query or the body is `invalid_request` | RFC 6750 §2: one method per request. Tokens in URLs and bodies end up in logs; OAuth 2.1 drops the query form. |
| Userinfo without usable credentials | `401` with `error="invalid_request"`, whether the header was missing or malformed; no `realm` | No credentials: `401` with `WWW-Authenticate: Bearer realm="…"` and no error code. A malformed `Bearer` header: `400 invalid_request`. Every challenge names the issuer as its realm | RFC 6750 §3.1: a request with no authentication information gets no error code, and `invalid_request` is a 400. |
| Profile claims | Any string in the column | Names of at most 255 characters without control characters, `picture` an http(s) URL, `locale` a BCP 47 tag | They are copied into signed tokens; the domain refuses what no relying party should receive. |

## Login page and sessions

| Area | Python | PHP | Why |
|---|---|---|---|
| A throttled sign-in attempt | Refused at once, without hashing anything | Refused after the same time a password check takes | A faster answer would tell an observer the account is locked — and so that it exists. |
| Theme toggle on a login page re-shown after a failed attempt | Came back to `/auth/login`, losing the pending authorization request | Comes back to `/auth/login?state=…` | Switching colour scheme must not cost the person their place in the flow. |
| `next` on `POST /auth/logout` | Any `https` URL on a registered origin | The same, without a fragment | Nothing legitimate needs one there, and a fragment is never checked by anyone. |
| Session record in Redis | A hash, plus a per-user index and a per-session client index | One JSON document per session; the two indexes come with session management and back-channel logout (Step 17) | Not visible over HTTP. Nothing reads the indexes yet. |
| The session's connection | Recorded | Not yet recorded | Connections arrive in Step 13, with the check that uses the value. |

## Errors shown to browsers

| Area | Python | PHP | Why |
|---|---|---|---|
| 404 and 405 | `{"detail": …}` for every caller | The same for a program; a page for a browser (`Accept` naming `text/html`) | A person who follows a dead link should read a sentence, not a JSON document. Programs keep the body they parse. |
| `/oauth2/authorize` error that cannot be redirected (unknown client, unregistered redirect URI) | A JSON error document | The same for a program; a page for a browser, explaining what happened, with the error code as a reference and no link onwards | RFC 6749 §4.1.2.1: the resource owner is to be informed, and the resource owner is in a browser. |
| An uncaught error (500) | `Internal Server Error` in plain text | The same for a program, plus `X-Error-Reference`; a page with the reference for a browser | The reference is in the log next to the cause, so a person can report the failure without the server describing it. |

## Tooling (not user-visible)

- Console commands are built on `symfony/console` directly rather than `laminas-cli`, which wraps
  it: `bin/clavia <command>` keeps the Python command names without a second binary.
- The licence header is enforced by a test (`LicenseHeaderTest`) instead of an extra tool.
- The auth pages are laminas-view PHP templates rendered through Mezzio's
  `TemplateRendererInterface`, where Python used Jinja2. Markup and the stylesheet are the same.
